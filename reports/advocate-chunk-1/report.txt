Counter meaning and design sources
Design 184/443 supplies the existing list layout; design 162 supplies its advocate
REVIEW / PROGRESS / RESOLVED grouping, Needs Review / In Progress and Open Case.
Upcoming is scheduled work in the generic fixtures, not a Legal Notice lifecycle.
For API Legal Notices:
- REVIEW: assigned requests awaiting the advocate's acceptance.
- PROGRESS: accepted, in_progress, changes_requested, client_review, approved,
  dispatching, dispatched. Waiting for Client is the client_review subset.
- RESOLVED: completed, cancelled, refunded, or declined by this advocate.
  Resolved describes this advocate's work; a declined case can still await admin
  reassignment. It is not represented as a globally completed case.
Defensive pre-assignment statuses (draft/submitted/payment_pending/paid/assigning)
remain in REVIEW if ever supplied for this advocate, with no action. Normally the
advocate-scoped endpoint cannot return those unassigned cases.
The three groups partition the records; no case is counted twice or omitted.
Counters respect search and service scope. Status filters narrow the cards, while
the counter strip remains the breakdown of the scoped list. The Your Matters
badge is the actual visible row count. Recent First uses updated_at descending.
API service filters offer All Services and Legal Notice only; other APIs are not
built by this chunk. Fixture services/filters remain available as before.

Action mapping
assigned                 Review Request -> fee (184)
advocate_accepted        Continue Draft -> drafting choice (443 label)
in_progress              Continue Draft -> draft editor (443 label)
changes_requested        Continue Draft -> drafting choice (starts resume first)
client_review            Open Case -> review (162 label)
approved                 Open Case -> final notice (162 label)
dispatching/dispatched   Open Case -> dispatch (162 label)
completed                Open Case -> existing report (162 completed-card label)
advocate_declined        no action; actual Declined status remains visible
cancelled/refunded       no action; actual status remains visible
pre-assignment states    no action

Declined/cancelled/refunded have no drawn read-only advocate destination. The
entry list does not send them to the old fee/acceptance fallback. Per-case screens
are unchanged. Every navigable record retains caseId. Existing drafting choice is
used after acceptance/change requests so the real start transition is not skipped.
The whole real notice card is no longer an HTML button around another button;
only its explicit action is interactive, removing browser nesting errors.
Missing tier, body or footer removes that element, without a fallback fixture.
